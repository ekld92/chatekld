# Library Audit — Deep Notes

Loaded on demand when working under `audit/`. The two hard invariants (manual-only scan, read-only posture) are restated in the root `CLAUDE.md`; everything here elaborates on them.

- **Manual-only invariant.** No code path outside `POST /api/audit/scan` may call `audit_manager.start_scan()`. `app.py:create_app()` is required to leave the audit `idle` — `test_audit.py::TestFlaskAppBootDoesNotScan` pins this with a `mock.patch.object(audit_manager, 'start_scan')` spy and will fail loudly if a future change adds an auto-scan hook.
- **Read-only posture — one vault-write exception (2026-07-12, axis ii).** External stores (Zotero, Finder tags, BibTeX, PDFs) are opened read-only and never mutated, and the scan itself writes nothing. The single vault-mutating action is `POST /api/audit/apply-tag-drift` (route layer, NOT the vendored engine) — the Finder vs Note Tags fix verbs (2026-08-06) are not a second one: they POST to the *tagging* subsystem's journalled writers, so the audit surface inventory is unchanged. `apply-tag-drift` merges missing Zotero tags into one Obsidian note's `tags:` frontmatter via `api/routes/_audit_tagwrite.py` — tags server-intersected with the record's real drift set, confirm-gated, obsidian op-lock held, non-clobbering `.bak` (the first backup is the true original and is never overwritten by later applies), `log_vault_write("audit_tag_add", …)`, and a post-merge YAML round-trip guard that refuses (422) instead of writing a frontmatter that doesn't re-parse to exactly `before ∪ added`. The vendored `audit/` tree stays read-only; the writer lives entirely in the app route layer. The Zotero snapshot (`audit/core/zotero.py::_open_snapshot`, hardened 2026-07-02 — improvement plan 0.7) copies `zotero.sqlite` + any `-wal`/`-shm` siblings to a temp dir (2 GB ceiling), opens the COPY with `mode=ro` (never `immutable=1`, because committed WAL must be read), and `backup()`s it into a throwaway `:memory:` connection. Source main/WAL/SHM signatures are checked during copying. A changing/torn copy or files over the ceiling falls back to direct `mode=ro` + SQLite backup, which can take live read locks and interact with SHM; do not promise zero SQLite locks. PDFs are opened with `pikepdf.open(...)` for header/annotation walking only. BibTeX, frontmatter and Finder xattrs are read in place. The engine tree's only *hand-curated* writable file is `BASE_DIR/audit/mapping.json` (manual PDF↔bib overrides + the two curated buckets `no_match`/`pending` + the `detach` exclusions `exclude: {rel: [key…]}` + the per-entry `hashes` anchoring map `{rel: {sha256, size}}` + the `sources` provenance map) — the regenerable `hash_cache.json`, the regenerable `doi_cache.json` (the DOI rung's memo AND, since 2026-08-26, the residual-PDF provenance memo under a `prov` field — see below) and the two decision sidecars `dup_decisions.json` and `pdf_wanted.json` (all described below) are the other four files the vendored tree writes. mapping.json is reached only through `audit/engine/bridge.py::add_match` / `add_no_match` / `clear_curation` from the `POST /api/audit/mapping` route, plus the scan-time `refresh_mapping_hashes` (called from `audit/manager._run`, never per-POST — restoring a per-POST call would re-open the fixed O(curated)-hashes-per-click perf bug); loads go through the single-read `_load_mapping_full` (no torn matches/hashes pair), hashing runs OUTSIDE the RMW lock, and the atomic writer `fsync`s before the rename (W6 durability — the file is hand-curated and unregenerable). Hash recovery at scan (`build_bridge` Step 1b, source `manual_hash`) is size-prefiltered, capped at 500 hashed candidates per scan (WARN when hit), refuses duplicate-digest ambiguity, and surfaces lingering dead entries as `summary.mapping_orphans`.
- **Step 0: the Zotero link (2026-09-19).** Above everything, including `mapping.json`: a PDF exactly one Zotero item links as a `linked_file` belongs to that item's key (source `zotero_link`); `build_inventory` therefore reads Zotero before the bridge and passes `inventory.zotero_link_index`. Hand decisions it overrides are reported (`BridgeResult.zotero_overrides` → the `dead_curation` kind `overridden_by_zotero`), never rewritten by the scan; a PDF linked by two items, or by an item Better BibTeX has not exported, falls through to the ladder below. Full rationale in the root `CLAUDE.md` Library Audit rules; tests in `tests/audit/test_bridge_zotero_link.py`.
- **DOI resolution rungs, split by evidence class (2026-08-19).** `build_bridge` gained two identifier steps around the author+year heuristic, because a measurement of the live library found 968 unmapped PDFs of which **390 were already in `_master.bib`, merely unlinked** — step 4 had missed them because the filename year and the bib year disagree (online-first vs issue year: 235 of 264 year mismatches were exactly ±1) or the surname was transliterated differently (`boege`/`böge`, `vandebroucke`/`vandenbroucke`). Loosening step 4 to a fuzzy ±1 match would trade those misses for false positives across 5,442 files; an exact DOI needs no threshold. **The split is the load-bearing part.** A DOI in a PDF's *embedded metadata* is the publisher asserting an identity for that file, so **step 3.5** trusts it and runs BEFORE author+year — it can correct a surname-and-year coincidence (20 real corrections, e.g. `solmi_2024.pdf` → `solmiEfficacy…2025`). A DOI *printed in page-1 text* may belong to a neighbouring article on the same journal page, so **step 4.5** runs AFTER author+year and can only fill a gap, never overrule a match: allowing printed DOIs to override produced 13 wrong re-assignments on the measured library (a World Psychiatry page resolving to its neighbour's DOI, `luykx_2023.pdf` → a Teo paper). Both classes recover equally well (237 + 152 of the 389), so the split costs nothing in recall. Sources are `doi` and `doi_text`; a DOI carried by >1 bib entry is refused (the standing never-guess posture) and recorded in `BridgeResult.doi_collisions`, which is a duplicate-BIB-ENTRY finding worth surfacing on its own. Extraction lives in `audit/core/pdf_identifiers.py` (pikepdf `/Info` + XMP, plus the `_DOI_RE`/`_ARXIV_RE`/`extract_printed_identifier` trio **moved there from `engine/near_duplicates.py`**, which now imports them — required by the import graph, since near_duplicates imports *from* bridge). **`BASE_DIR/audit/doi_cache.json` is not an optimisation:** step 3.5 examines everything steps 1–3 left unclaimed (~4,980 files, not the ~968 residual, precisely because author+year runs after it), which is **+52 s per cold scan**; the memo takes the warm scan to **0.4 s**. It caches the `meta` and `text` classes independently — a cached "no DOI in the metadata" says nothing about the text — and caches negatives, which is where most of the saving comes from. Pinned by `tests/audit/test_bridge_doi.py`.
- **Residual provenance, and the memo contract that makes it cheap (Batch C, 2026-08-26; repaired 2026-08-26).** `bridge._classify_residual` gives every UNMAPPED PDF a physical class via the pure `audit/core/pdf_provenance.py`, so the UI stops offering a DOI search to a printed web page. It rides the pikepdf open `extract_embedded_doi` already performs (both now go through `read_pdf_meta`) and memoises into the SAME `doi_cache.json` entry under a `prov` field. **`doi_cache.lookup` returns the stored value verbatim** — it used to coerce anything non-`str` to `None`, which made a `prov` hit indistinguishable from a miss and the memo entirely dead (11.8 s of re-opens per scan on 371 files); DOI consumers coerce at the call site via `bridge._cached_doi`, so a hand-edited cache still cannot leak a non-string into the join. Entries carry **`text_seen`** because the `(size, mtime_ns)` key cannot tell a scan that had a page-1 text source from one that did not: the CLI path injects no `pdf_text_provider`, and without the flag such a run would durably memoise "no source URL" for every printed web page. Classification is producer/creator substrings — note that these are SUBSTRING tests, so a bare `"tex"` matched `Quartz PDFContext`, and `quartz pdfcontext` is itself the generic macOS print producer rather than a browser fingerprint and needs corroborating by a browser `/Creator` or a recovered URL. Pinned by `tests/audit/test_pdf_provenance.py`.
- **bib ↔ Zotero identity: the BBT citation key, with a deliberately timid title fallback.** `_master.bib` entries join to Zotero items on the Better BibTeX `citationKey` field (`audit/core/zotero.py` reads it from `itemData`; `inventory._index_zotero_by_citation_key`, first-wins, loser left unjoined). This decides which external item `apply-zotero-tags` writes to, so a wrong join tags someone else's paper — it did: joining by normalized title left 23 items claimed by 2+ keys across 51 records, and 10 real mis-directed writes had to be repaired 2026-08-12. **The fallback is the part to be careful with.** It runs in a SECOND pass (`_resolve_title_fallback`), after every key join is known, and refuses three ways rather than guessing: an ambiguous title (naming >1 item — the index keeps collisions instead of collapsing them first-wins), an item already **claimed** by the authoritative key join, and two unjoined records contending for one item (refusing both, because `all_keys` is a set and "first wins" would pick a different record per run). The claimed-item refusal is what closed the 2026-08-12 residue: with a STALE bib key (item re-keyed in BBT after the last export) and a title collision, the fallback re-claimed a paper that already belonged to another record. Unjoined is recoverable — the writers report `skipped: no_item` — a wrong write is not. Diagnostics: `zotero_matched_by_key` / `zotero_matched_by_title` (both in RECORDS since 2026-08-12; the title figure counted distinct titles, so the advertised ratio compared different denominators) plus `zotero_title_refused`, a non-zero value being the fallback declining to guess, not an error. Pinned by `tests/audit/test_zotero_join.py`.
- **Vault path source of truth.** The audit reuses `obsidian_vault_path` from the main config — no separate vault key. Every other subpath (`audit_attachments_subdir`, `audit_biblio_articles_subdir`, `audit_zotero_notes_subdir`, `audit_master_bib_path`) is configurable via the Library Audit settings modal and validated through the same `api/validators.py` helpers the vault routes use (path-traversal rejected, absolute paths rejected, max-length capped). The generic `POST /api/config` strips `audit_*` keys so those validators cannot be bypassed.
- **`scan.py` is a printer, not a checker.** Every `check_*` in `audit/scan.py` returns `0` unconditionally; `main()` goes non-zero only when a check *raises* (1) or the config is missing (2). That is the CLI's contract and it stays — but it means `python -m audit --check <name>` can never be wired into a pass/fail runner, because the resulting step is green no matter what it finds. A pass/fail maintenance runner must therefore import the engine directly rather than shell out to `--check`, build the inventory **once** and share it across the dimensions that need it (separate `--check` calls each rebuild the full Zotero + PDF inventory, ~9 s a time; `duplicates-biblio` is the exception, hashing from `settings` instead), and apply its own measured thresholds. Such a runner also wants `tag_hygiene`, which has no `--check` at all — it is otherwise reachable only via `GET /api/audit/reports/tag_hygiene`. If you add a `check_*` here, it inherits the always-zero contract, so a threshold for it belongs in the runner. *(The maintainer's own runner lives in the private-only vault-maintenance tooling — see the note at the end of the root `CLAUDE.md` Tests section.)*
- **Settings adapter.** `audit/config.py::load_settings()` builds a kb_harmonizer-shaped `Settings` dataclass from the active CHERQAiN config. It raises `AuditConfigError` when `obsidian_vault_path` is empty or does not exist on disk; the route layer surfaces that as a 400.
- **Background lifecycle.** `audit/manager.py::AuditManager` runs one scan thread at a time. State machine: `idle → scanning → done | error | cancelled`. Cancellation is cooperative via `_stop_event` checked between phases (after inventory build, after duplicates, after near-duplicates). The pikepdf annotation read on a single PDF is NOT interruptible. A new scan started while the previous is still finalising is stamped with a fresh `_run_id`; the stale completion drops its result on the floor instead of overwriting the live one.
- **Result cache.** Inventory, duplicate and near-duplicate sets are held in memory only — no on-disk cache. `GET /api/audit/inventory` and `GET /api/audit/reports/<name>` return 404 until a scan completes. `clear_results()` (drops all three sets) exists for tests; production code never calls it.
- **Duplicate-scan infra (plan 2026-08-05/4).** (a) `BASE_DIR/audit/hash_cache.json` (`audit/core/hash_cache.py`) memoises full-file sha256 keyed `(size, mtime_ns)` — the audit's own copy of the RAG `pdf_signatures` pattern (vendored tree can't import it); the manager loads/saves it around the duplicates phase, `find_duplicate_sets(hash_cache=…)` short-circuits memo-valid candidates past BOTH read stages (and the unique-partial prune is suppressed when a memo hit exists in the size group, so a memoised file still pairs with a byte-identical newcomer whose partial hash is unique), and the bridge's hash-recovery pass consults it READ-ONLY (the duplicates phase owns the save — one writer). Atomic write, no fsync (regenerable — the mapping.json writer's fsync is for unregenerable data), stale keys pruned at save. Unreadable files are now counted + WARNING-logged instead of silently dropping out. (b) The candidate walk (`duplicates.candidate_pdfs`, shared with the near-dup engine) prunes `ignored_dirs` like every other walk (a `.trash` copy no longer forms a set); `biblio_skip_prefix` files stay deliberately included. (c) `report_duplicates` carries `suggested_keep` — the set member whose filename scores cleanest per `core/naming.py` (previously dead code), starred in the UI; advice only, no delete action. (d) `BibEntry.doi` (additive; `bib.normalise_doi` strips URL/`doi:` prefixes, lowercases, refuses non-`10.x/…` shapes). (e) `manager.start_scan(pdf_text_provider=…)` — the route-injected, cache-first, page-1-bounded PDF-text callable (`api/routes/audit.py::_build_pdf_text_provider` over `tagging/text_source.py`) the near-duplicate tiers consume; `None` on the CLI path degrades them to hash-only. Pinned by `tests/audit/test_duplicates_infra.py`.
- **`read_unzoterod` ⊃ `unread_unzoterod` — they are NOT a partition.** Both walk the same `inv.bridge.unmapped_pdfs`; `read_unzoterod` applies **no filter at all** (every un-Zotero'd PDF, read and unread, ranked by annotation count desc), while `unread_unzoterod` keeps only `annotations < annotations_read_threshold`. Until 2026-07-31 the two tabs were labelled "Read PDFs Missing Zotero" / "Unread PDFs", which reads as a partition and hid the complete list from the user — they now render as **"PDFs Without Zotero"** and **"↳ Unread Only"**, adjacent and superset-first, in `templates/index.html`; `audit.js::_REPORT_LABELS` deliberately spells the subset's parent out (`PDFs Without Zotero · Unread Only`) because the same strings head the cross-report search groups, where the arrow is meaningless — keep the *pairing* in sync, not the literal strings. The containment is pinned by `test_audit.py::TestUnzoterodReportsUseCache::test_reports_serve_from_cache_without_disk_reads`. `read_unzoterod` additionally carries **exclusion disclosure** — `ambiguous_count` / `confirmed_no_match_count` / `skipped_count`, counts only, never rows — because `unmapped_pdfs` is just one of the bridge's residual buckets and the skip-prefix files never reach the bridge, so "every unmapped PDF" ≠ "every PDF missing from Zotero". Pending PDFs (2026-09-06) are ALSO identifiable by the accession routes (`_resolve_orphan` admits `pending_pdfs`; `no_match` stays refused) so the Not in Zotero tab can resolve them for the DOI hand-off. Confirmed-no-match PDFs stay counted-but-unlisted HERE (listing them would re-clutter this queue) — since 2026-09-06 they have their own tab, `not_in_zotero`, because the measured bucket (291 files, 203 with a resolvable DOI) was mostly "add to Zotero later", not "never a paper". The same three counts print from `audit/scan.py::check_read_unzoterod`.
- **Unmapped-PDF annotation precompute.** The `unread_unzoterod` and `read_unzoterod` reports both iterate `inv.bridge.unmapped_pdfs` and need each PDF's annotation count. Computing that lazily inside the `GET /api/audit/reports/<name>` handler opened thousands of PDFs on the request thread (the "Unread PDFs" tab hung on "Loading…" while pikepdf churned). Instead, `inventory.build_inventory` precomputes those counts during the scan — gated by the same `count_annotations` flag, **parallelised** via `ThreadPoolExecutor` (cap `_ANNOTATION_MAX_WORKERS = min(8, cpu_count)`; pikepdf/qpdf releases the GIL so threads scale) — and caches them on `Inventory.unmapped_annotations: dict[Path, AnnotationsResult]`. The route passes that dict into both reports' `find(..., annotations=...)`. `find()` still falls back to a lazy `read_annotations` for any path **missing** from the dict, so a `count_annotations=False` run (empty cache) or a scan cancelled mid-phase (partial cache) degrades to the old per-request read instead of breaking. Progress lines (`Reading annotations for N unmapped PDFs…`, then `…done/total` every 500) flow through `build_inventory(progress_fn=...)` → `manager._emit` into the status feed. Note: the scan's *mapped*-PDF annotation reads (`Record.annotations_count_max`) remain serial — they're the smaller set and not the bottleneck; consolidating them into the same pool is a deferred follow-up. **Sharp edges (by design):** a `count_annotations=False` scan leaves the cache empty, so opening these two tabs falls back to the full serial on-request read — the original "Loading…" stall returns in that mode; and a *cancelled* scan caches only a partial map, so viewing the tabs afterwards lazily reads the un-cached remainder on the request thread (still strictly less work than the pre-optimisation path, but not free).
- **macOS-only Finder tag reads.** `audit/core/finder_tags.py` short-circuits to an empty list on non-Darwin platforms (the `_load_libc()` guard). The audit therefore degrades gracefully on Linux/Windows test runners but the Finder tag dimension is silently empty there.
- **Frontmatter parse warnings are user-visible.** `audit/core/obsidian.py` collects YAML frontmatter-parse failures into a drainable buffer (`drain_parse_warnings()`, deduped, capped at 100); `audit/manager.py::_run` drains it after the inventory phase and emits the first 5 plus a count into the status feed, since a skipped note means its tags are invisible to `note_tag_drift`. Notes are also cached by `(path, mtime_ns)` in `read_note` — `bridge.py` and `inventory.py` both walk `Z_Zotero_Notes` within one scan, so the second walk (and unchanged-note rescans) is free; a cache hit on a malformed note re-records its warning so the problem never silently looks fixed.
- **macOS-only `reveal` endpoint.** `POST /api/audit/reveal` returns 501 on non-Darwin. Paths are bounded to `settings.vault_root` or `settings.zotero_storage` so a malicious request body cannot point `open -R` at arbitrary files. Zotero items open via the `zotero://select/library/items/<key>` URL handler.

## `/api/audit/*` endpoint details

- `POST /api/audit/pdf-decision` is also reachable headlessly since 2026-09-06 (`papermind audit pdf-decision --keys/--keys-file --dismiss|--clear|--clear-all`, driver `audit_pdf_decision`).
- `GET /api/audit/status` — `{state, error, started_at, finished_at, has_results, has_duplicates, has_near_duplicates, messages[]}`. Polled by the UI only while `state == "scanning"`.
- `POST /api/audit/scan` — body `{count_annotations: bool?, include_duplicates: bool?, include_near_duplicates: bool?}` (each defaulting to true). The ONLY entry point that starts a scan. 409 if one is already in flight, 400 if config is incomplete. The route also builds and injects the near-duplicate tiers' page-1 `pdf_text_provider` (`_build_pdf_text_provider`).
- `POST /api/audit/dup-decision` — body `{pair_id, dismiss: true}` | `{pair_id, clear: true}` (`clear` = undo, checked first). Writes only `BASE_DIR/audit/dup_decisions.json`; details in the `near_duplicates` bullet above.
- `POST /api/audit/pdf-decision` (2026-08-26) — `{citation_keys:[…], dismiss:true}` | `{citation_keys:[…], clear:true}` | `{clear_all:true}`, undo verbs checked first. Writes only `BASE_DIR/audit/pdf_wanted.json` — the MIRROR of `mapping.json`'s `no_match` list, without which *Bib Entries Without PDFs* could only grow. Takes a LIST so a bulk "dismiss every webpage" is one atomic write. **Unlike a mapping edit it applies on the next report LOAD, not the next scan**, which is why `zotero_no_pdf` filters at render time — and why the cross-report search reads the dismissal set fresh per query (`search(corpus, q, hidden_keys=…)`) instead of baking it into the per-scan memoised corpus. Filtering it in `build_corpus` would force a rebuild per decision; not filtering it at all left a dismissed row findable in search but absent from the tab, breaking the corpus's "a hit is a row you can go and look at" invariant.
- `POST /api/audit/cancel` — sets the manager's `_stop_event`; the worker checks between phases.
- `GET /api/audit/inventory` — `{summary, records}`. 404 until a scan completes.
- `GET /api/audit/reports/<name>` — `name` ∈ `{note_tag_drift, finder_tag_drift, tag_harmony, unread_unzoterod, zotero_unread, read_unzoterod, zotero_no_pdf, duplicates, near_duplicates, ambiguous_pdfs, skipped_pdfs, tag_hygiene, orphan_notes, orphan_zotero_items, zotero_attachments, multi_pdf, not_in_zotero, dead_curation}` — **eighteen**, and `api/routes/audit.py::_REPORT_NAMES` is the authority (`core/driver.py::AUDIT_REPORT_NAMES` mirrors it for CLI/MCP and `tests/test_mcp_server.py` pins the two agree); this list drifted three behind it between 2026-08-13 and 2026-08-26, and one behind again (`zotero_attachments`) until 2026-09-06. The three 2026-09-06 names are the read-only harmonization views (root `CLAUDE.md` → API Routes): `multi_pdf` (records owning ≥2 PDFs, per-file rung, `engine/reports/multi_pdf.py`), `not_in_zotero` (the curated `no_match` bucket — listed here and nowhere else; the accession join is route-injected), `dead_curation` (mapping.json entries pointing at a missing file or a dead key, and since 2026-09-19 those the Zotero link overrides, `engine/reports/dead_curation.py`). (`tag_harmony`, the three-way writable-surface comparison, and the two `orphan_*` buckets are documented in the root `CLAUDE.md`; the "Zotero Notes Sync" tab is NOT one of these — it has its own `/api/notesync/status` route so the vendored tree keeps its read-only posture.) **`note_tag_drift` compares by fingerprint, not raw strings (2026-08-05):** both sides go through `audit/engine/normalize.py::tag_key` (the OpenRefine fingerprint shared with Tag Hygiene, with an NFC+casefold fallback for non-Latin tags that fingerprint to `""`), so case/accent/NFC/separator differences are no longer "missing" — a tag present under another spelling lands in the additive per-row `variants` field (`[{zotero, note, reason}]`, reason ∈ `spelling`｜`synonym`; informational, never applyable), and `missing_in_obs` means absent in EVERY form. Rows are emitted when either set is non-empty, most-missing-first (variant-only rows sink). The route's `apply-tag-drift` intersection is keyed on the SAME helper (`note_tag_drift.missing_by_key`), which closed the unresolvable-row loop: a case-only "drift" used to pass the old `.lower()` check, then no-op in the writer's case-insensitive dedup ("Tags already present") and reappear every scan. Pinned by `tests/audit/test_note_tag_drift.py` + `test_audit.py::test_apply_tag_drift_refuses_variant_spellings`. **Drift coverage (plan 2026-08-05/3):** the drift report also carries the read-only reverse direction (`note_only` — note tags absent from the Zotero side; never actionable, Zotero writes belong to the tagging subsystem) and, behind the validated bool `audit_drift_include_parent_tags` (default off, Audit Settings checkbox, read fresh at request time so no rescan is needed), the Zotero *item*'s own tags — item-only missing tags are surfaced in `item_only_missing` so the UI badges "(item)". Both drift routes (report + `apply-tag-drift`) and the search corpus share TWO route-injected options resolved by the same helpers (`_drift_include_parent_tags` / `_drift_synonyms`) so report, write path and search can never disagree: the synonym map is built from the vault's `_tags.md` **single-tag** rows only (a multi-tag row asserts co-occurring facets, not synonyms — `rag/thesaurus.py`'s own rule), mapping each description phrase's `tag_key` to the tag's; a pair unified only by it is a `variants` entry with reason `synonym`. **`finder_tag_drift`** (2026-08-05) is the per-paper Finder-vs-note comparison Tag Hygiene's global counts could not answer: records with an Obsidian note, ≥1 PDF **and ≥1 Finder tag** (the asymmetric gate — `note_only` vs an untagged PDF would be noise, and non-macOS runs produce an empty report, not a flood) get `finder_only`/`note_only` via the same `tag_key`+synonyms comparison, plus (2026-08-06) `variants` — present-both-sides spelling near-misses via the shared `variant_pairs`, so a variants-only row IS emitted — and `note_path`. **Correctable since 2026-08-06, but the write still never enters the audit tree:** the serializer (`report_finder_tag_drift(rows, settings, vocab_id_for=…)`) additionally ships `note_rel` + per-surface `vocab_ids` (the route-injected `api/routes/audit.py::_vocab_id_resolver` — `_tags.md` ids indexed by `canonical_tag_key` with the SAME `_drift_synonyms` map as the comparison, the apply-tag-drift key-recipe lesson), and the UI's per-row `[→ note]` / `[→ Finder]` / `[+ vocab]` verbs POST those ids to the **tagging** writers (`apply-note-tags` / `apply-finder-tags` / `add-vocab-tag` — confirmInline-gated, journalled, per-op undo via `/api/tagging/restore`; out-of-vocab surfaces are badged not-applyable). Pinned by `tests/audit/test_finder_tag_drift.py`, `test_audit.py::test_finder_tag_drift_report_carries_fix_fields` and `tests/js/auditFinderDriftApply.test.js`. `ambiguous_pdfs` lists the bridge's parked multi-candidate PDFs (`{pdf, candidates:[{citation_key, title}]}` rows — the UI's picker resolves one by POSTing to `mapping`); `skipped_pdfs` lists the `biblio_skip_prefix`-excluded files; `tag_hygiene` is the read-only cross-store tag view (`engine/reports/tag_hygiene.py`): frequencies per source (Finder / note YAML / Zotero parent / Zotero child notes / bib keywords) grouped by fingerprint, `_tags.md` vocabulary flags (resolved via `api/routes/tagging._read_vocab` — same config key, `vocab=None` tolerated), near-miss neighbours (`difflib` ≥ 0.85) and top co-occurrence pairs. Its fingerprint recipe lives in `audit/engine/normalize.py` since 2026-08-05 (shared with the drift comparison — one definition of "same tag"; still vendored-tree-local and stdlib-only, per the `audit/config.py`-only dependency rule; `tag_hygiene._fingerprint` remains an importable alias). - **`near_duplicates` (plan 2026-08-05/5)** — `audit/engine/near_duplicates.py`, the evidence-tier candidate engine over byte-DIFFERENT files the exact scan cannot see. Tiers: `page1_text` (normalized first-page token key — alphabetic tokens ≥3 chars, accent/case-folded, digits dropped so watermark timestamps/IPs cancel; <20 tokens counts as no-text), `identifier` (first DOI/arXiv id on page 1, version suffix folded so v1/v2 pair; nearest-the-top wins — pdf2doi's cited-DOI failure mode), `bib_doi` (two `.bib` records sharing `BibEntry.doi`), `multi_pdf` (one citation key, ≥2 byte-distinct PDFs), `record_title`/`title_only` (normalized-title collisions, `record_title` when Zotero-style confirmed: year ±1 AND same normalized first-author surname). ## Association evidence correction (2026-10-04)

A successful Zotero read now passes an explicit link index (including an empty
one). In its absence, pass None: a failed observation cannot establish absence.
With an observed index, PDFs without a linked attachment cannot be claimed by
fm_pointer, fm_authoryear, wikilink or authoryear. This prevents an old note from
recreating a removed attachment association. Manual and DOI matches keep their

legacy basename projection. Shared pdf_files discovery includes mixed-case PDF
extensions across inventory, reconciliation, duplicates and CLI. These rules
never rewrite vault notes or mapping decisions.
